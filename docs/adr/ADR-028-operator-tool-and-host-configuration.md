# ADR-028: Operator tool and host configuration

Status: Proposed. Drafted 2026-11-21 by lane L19 `prod/fstp-admin`; lead readings recorded on 2026-11-22. Rows marked "Decided by Daniel on 2026-11-21" record his direction. Every other row is interim, pending Daniel. The rows were written before the code, as CLAUDE.md asks.

## Context

Daniel, 2026-11-21: "This all sounds very complicated to use, people shouldn't need a PhD to run this platform. It should be runnable by two people, and usability should win over security theater."

- Two operators run a host. One technical admin uses SSH and a terminal and is not a cryptographer. One non-technical person uses only the web app.
- The production guide asked the admin to write six configuration files by hand, mint about thirty certificates, create PostgreSQL roles, register keys with the witness and order a dozen commands. Several steps had no instructions at all, such as the database roles, the migrations and the witness keys.
- The pilot must stay close to production, so the tool is the one production will use.
- Applicant-facing invariants stay untouched. This ADR removes operator ceremony only.
- The design of the cell's files is ADR-026. The key file and custody are ADR-004. Backups are ADR-012. The edge and routes are ADR-009.

| No service library in `fstp-admin` | `fstp-admin` links no service crate (`fstp-cell`, `fstp-vault`, `fstp-witness`, `fstp-keyd`) and no custody client. Nor `fstp-control`. Layering rules 2, 3 and 7 of the M3 design forbid most of them. | Witness key commands | `fstp-witness` gains `init-keys <dir>`, which creates its receipt key file through its own custody entry and writes `receipt.pub`, and `register <cell> <cell-ca.pem> <app-anchor.pub> <vault-anchor.pub>`, which registers a cell in a self-hosted witness's file store with the witness stopped. Before this, the receipt key file had no command at all | ADR-004 part 2 "Self-hosted witness receipt key"; interim reading |
| One-host witness | A single-host pilot runs its witness in the self-hosted file-store form, on loopback. No witness database is needed | ADR-010 open point 6; interim reading |

Until Daniel decides, `setup` stops at the witness step on a host with real `fstp-keyd`, and says why | ADR-004 part 2; open point |
| Custody entries | Four `fstp-keyd` entries per host: `cell` (App and CellBackup chains), `cell-keys` (the dedicated root of the cell key file), `vault` (Vault chain) and `witness` (ControlPlane). Each has its own volume, socket directory and random passphrase. The app cluster's backups use the console socket of `cell`, the vault cluster's backups that of `vault` | ADR-004; ADR-009 B9; R-NF-08 |
| Several `fstp-keyd` on one host | `fstp-keyd` serves the fixed paths `/var/lib/fstp-keyd` and `/run/fstp-keyd`. The systemd template unit `fstp-keyd@.service` maps `/var/lib/fstp-keyd-<entry>` and `/run/fstp-keyd-<entry>` onto them with `BindPaths=`. `fstp-keyd` itself is unchanged | Interim reading |
| Passphrases | `setup` draws each passphrase from the system random source and stores it as a root-only file under `/etc/fstp/keyd`, loaded with `LoadCredential=`. So the host boots unattended. `setup` tells the admin once to copy the four passphrases off the host. `backup-keys` copies are useless without them. Encrypting the credentials to a TPM with `systemd-creds` is a later step | R-NF-05; ADR-004 part 2 "Unattended boot"; interim reading |
| Verify the first admins | `fstp-admin verify <account> [<file>]` asks for the family names, given names, date of birth and issuing state the technical admin checked in person, or reads them from a JSON file. It stops the vault, runs `fstp-vault verify-first-admin <account> <file>` (lane L13b) through a root-only file it deletes afterwards, and starts the vault again. It never prints or logs the details. `status` names it as the next thing to do once setup is complete | Coordinator, 2026-11-21; lane L13b interface pending |
| Routes kept current | `setup` adds the host's own route. `renew` issues the tunnel certificates again before they end and then puts the new pins into the route at once. `status` flags a route whose pins differ from the current certificates. The route feed pins one certificate per endpoint, so a renewal has a gap of one edge restart at most. `fstp-admin route` stays for rare manual cases | Coordinator, 2026-11-21 |
| Certificates | `setup` runs five private CAs on the host: the application cluster CA, the vault cluster CA, the cell CA, the tunnel CA and the witness CA. Their keys are root-only files under `/etc/fstp/ca`. Client certificates live seven days (`fstp_pki::cert::CLIENT_MAX_LIFETIME`). A daily `fstp-admin renew` timer renews any certificate with less than three days left and restarts the services that read it | ADR-005 D2; ADR-009 certificate table; interim reading |
| Cell CA key | ADR-009 puts the cell CA key in the cell's custody entry, created by the cell at first start. The cell does not do that yet, so `fstp-admin` holds it as a file, like the other host CAs | ADR-009; open point |
| Public origin certificate | The admin names a certificate and key for `<domain>` and `id.<domain>` from a public CA, for example from certbot. Without one, `setup` makes a self-signed origin and `status` says, as its next thing to do, that browsers will refuse it | Interim reading |
| PostgreSQL | `setup` creates two clusters with `initdb`, an application cluster and a vault cluster, each on loopback with its own CA, a server certificate whose OU names its kind, and `hostssl` lines with `scram-sha-256` and `clientcert=verify-full` only. No Unix socket. The superuser `fstp_super` logs in over loopback TLS with its client certificate, as `HBA_SUPERUSER_LINE` says. `fstp-admin` sets the login passwords and creates the empty database with CONNECT grants through `psql`, as the world harness does | ADR-005; ADR-011; I-82; I-83 |
| Database provisioning | `fstp-pgagent` gains the host command `run-job <job> [<database>]`. It runs one non-destructive job on the local cluster through the agent's own executor: `harden`, `create-database`, `create-roles`, `revocations`, `write-hba` and `grants`. No word names a destructive job, so those still need two approvals. `fstp-admin` renders no role plan, revocation, grant or `pg_hba` line of a cell itself | ADR-011 job table; interim reading |
| Layering | Rules 2, 3 and 7 of the M3 design keep `fstp-vault`, `fstp-cell` and `fstp-custody` out of reach. `fstp-control` and `fstp-witness` reach `fstp-custody`, so `fstp-admin` links neither. It depends on `fstp-json`, `fstp-crypto`, `fstp-pki` and `fstp-pgwire` only | M3 design section 2.4 |
| Migrations | `fstp-admin` reads each migration set from the installed directory `<share_dir>/migrations/{app,vault}`, files named `NNNN_name.sql`, and runs them as the database's migrator role. Applied versions are recorded in the admin state. A re-run of `setup` after an upgrade applies only the new files. A celltest ties the installed files to `fstp_pgstore::MIGRATIONS` and `fstp_vault::MIGRATIONS` | Design section 4.6; interim reading |
| Tenant provisioning | `setup` does not run `fstp-cell provision-tenant` on a pilot. Lane L12 records that a provisioned pilot cannot be activated yet. The configuration keeps `organisation_active` until then | ADR-026 "Tenant provisioning" |
| First admin | `setup` runs `fstp-cell first-admin` once, with `--email <operator_email>` where the cell supports it (lane L12). It writes the token file under `/root` with mode 0600 and prints only its path, never the token | D4; ADR-026 "First admin email" |
| Services | `setup` writes one systemd unit per service and starts them in dependency order: the keyd entries, PostgreSQL, the witness, the vault, the cell, the edge, then the backup timers. A `direct` mode starts the same processes without systemd, for a development machine and the end-to-end test. It is refused unless `FSTP_DEPLOYMENT_MODE=development` | Interim reading |
| Custody simulator | In `direct` mode only, the configuration may name `fstp-custody-sim` in place of `fstp-keyd`. Roots then live in memory and die with the process. This is the test seam of every other end-to-end test of the stack | Test seam; interim reading |
| Status | `fstp-admin status` prints one screen: each service with running or not, its health where it has a health check, the age of the newest base backup, the days left on the certificates, and one line "Next:" with the single most urgent thing to do | Decided by Daniel on 2026-11-21 (one screen); wording interim |
| Exit codes | 0 success. 1 something failed that the admin can fix and retry. 2 a refused configuration or argument. 3 `status` found a problem. 4 the step waits on a part that is not built yet | Interim reading |
| Human output (R-NF-02) | R-NF-02 bans free text on stdout and stderr in shipped crates. It is written for services, whose logs leave the host. `fstp-admin` is an interactive operator tool. Proposed exception: its human output goes through the one module `crates/fstp-admin/src/say.rs`, whose sentences are fixed text with typed slots (paths, service names, step names, counts). No slot ever holds an email address, a passphrase, a token, proposal content or an identity attribute. The R-NF-02 source scan (`crates/fstp-obs/tests/r_nf_02_shipped_source.rs`) admits the three functions `out`, `err` and `ask` of that module and nothing else. Interim, pending Daniel | R-NF-02; proposed exception |
| Logging of route changes | Each route change appends one line to `<state_dir>/admin/routes.log`: the time, the action, the host and the cell id. The route feed of lane L15 keeps its own audit chain | Interim reading |
| Erase an identity | `fstp-admin erase-identity <account>` stops the vault, runs `fstp-vault erase-identity`, and starts the vault again, also when the erasure failed | ADR-004 record of lane L13 |
| Backups | `fstp-admin backup` runs a base backup of both clusters now. `fstp-admin restore` stops the services, restores both clusters into new data directories, swaps them in, and starts the services. Backups need `backup.bucket`. Without it `status` names backups as the next thing to do | ADR-012 |
| Routes before lane L15 | On `main` the edge reads a route file. Until lane L15 merges, `fstp-admin route` edits that file and restarts the edge. Afterwards it calls `fstp-control route add` and `remove`. The seam is `crates/fstp-admin/src/route.rs` (`ROUTE_FEED`). With it on, `setup` also creates a `control` custody entry, the feed key (`fstp-control init-route-feed`), the `fstp-control route-feed` service and the feed form of `edge.json`. That mode passed the end-to-end test against `origin/prod/route-feed` at `dbed9a03` in a local trial merge. When lane L15 lands, turn `ROUTE_FEED` on, add `fstp-control` to the binaries of `tests/l19_admin_setup_e2e.rs` and of the CI devstack build | ADR-009 L15 |

## Open questions for Daniel (first draft, answered by the record above)

1. The R-NF-02 exception for `fstp-admin`'s human output (row "Human output").
2. The witness's ControlPlane custody entry (row "Witness custody"). Without a decision, a real host cannot run its witness under `fstp-keyd`.
3. File CA keys on the host, including the cell CA (rows "Certificates" and "Cell CA key").
4. Passphrases stored as host credentials, with the admin asked to copy them off the host (row "Passphrases").
5. The self-hosted file-store witness on a single-host SaaS pilot (row "One-host witness").
6. Restarting the services daily for certificate renewal, since they read certificates at start only.

## Consequences

- The production guide becomes a short how-to built around `fstp-admin`. The per-service detail moves to `docs/guide/production-reference.md`.
- A host has one file to edit and one command to run.
- `fstp-admin` holds no key material of a chain. It holds the five host CA keys and the passphrase credentials, as root-only files.
